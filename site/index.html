/3d

Ask an agent for a 3D hero and you get a default cube, washed-out colour, an 80 MB GLB and a “looks good” nobody checked. 3d decomposes your intent and references into a measured spec, builds against an approved brief and shots, and shows you versioned previews with captured evidence until you approve — for three.js and R3F, shaders, scroll-driven 3D, GLB pipelines and Blender.

The idea

Everything in 3d follows one idea: nothing is built before it is measured, and nothing is called done before it is captured.

Your request and every reference become a measured spec first — numbers a script took and judgements marked as such — then an approved brief and shots. Only then does the agent build, and it builds in versions: each one is previewed with a captured image for every shot, checked against the reference and the version before it, and judged by a fresh critic before you see it.

Your notes go back in as the next version, so the loop ends when you approve, not when the agent feels finished. The state lives in files — 3D.md and .3d/ — so the work survives a new session.

The loop in depth

One arc, seven steps: prepare, decompose intent and references, write the brief and shots, pick the approach, build, then preview and iterate until you approve, and record. Detection comes first, so the agent asks only for your decisions, each with a recommended answer. Commands here are written short; the real form is <skill>/scripts/<x>, run from your project root so .3d/ lands in the project.

The arc is for a new piece. Debug, add or change one thing, a Blender asset and review and iterate are their own lanes and skip intake and brief unless the change contradicts the approved brief.

1 · PrepareNo 3D.md: run scripts/capabilities, fill 3D.md from the template. Never installs. → shared-preflight.md
2 · IntakeReferences go through scripts/ref-extract and vision passes into .3d/reference-spec.json; missing detail is grilled in rounds of ≤ 6 questions. The turn ends on the restated brief and an explicit yes; with no live user it writes .3d/questions.md and stops, unless you said to assume defaults (then answers are tagged [assumed] in the brief). → intake-grill.md · intake-references.md
3 · Brief and shots.3d/brief.md, .3d/shots.json (shots.v1) and the chosen look in .3d/look.json (look.v1), all checked by spec-check. Work then passes five sign-off gates in order — brief, style frames, blockout, lookdev, final — each on your yes; a change that crosses an approved gate re-opens it. → brief-spec.md · brief-lexicon.md
4 · ApproachReal-time or pre-render, and the fallback ladder, recorded in 3D.md; it names the area files to read next. → brief-approach.md
5 · BuildRead only those files. One change-set per version via preview new-version.
6 · Preview and iterateCapture every shot, diff against the reference and the previous version, pass the fresh-critic gate (a new context, not told what was fixed), show the URL, version, change and a preview board contact sheet, map each note to the next version. Stop on the gate’s approval. → shared-preview.md
7 · RecordClaim-scoped verdicts, scripts/glb-report against the recorded budget, a version-log line in 3D.md. → shared-verification.md
Loop-back rule: three rounds on the same shot without convergence pauses the loop: the agent shows a before/after strip and asks whether the reference or the brief should change.

From reference to spec

“Make it look like this” becomes numbers before it becomes code. A mechanical pass measures what a script can; nine vision passes fill the rest; everything lands in one schema, refspec.v1, that the brief and the verification both read.

# every estimate is a leaf, never a bare number { "value": "soft", "confidence": "med", "evidence": "read" } { "range": [28, 50], "confidence": "low", "evidence": "inferred" } # measured numbers are copied unchanged

Every leaf says where it came from:

measured by ref-extract — never overwritten, only commented on.
read seen directly in the image or frames.
inferred a judgement, with a range and a confidence.

Checked, not trusted. spec-check validates refspec.v1, shots.v1 and look.v1 files; exit 1 names the bad fields. Honesty limits are in the schema. Focal length is only reliable as a class (ultra-wide to long); EXIF overrides any visual estimate; one vanishing point gives no focal length; palette mixes albedo with light, so material colour comes from an unshaded region. Scale is unknown unless a known object is visible. Several references with a role and weight are reconciled into conflicts[], not averaged. → refspec.md · refspec-mapping.md · intake-references.md

The preview tool

preview is how you review: a viewer for each version, a captured PNG for every shot, an A/B split against any other version or the reference, a storyboard contact sheet, and notes pinned to the image that the agent reads back and maps to the next version. All subcommands take --dir (default .3d).

CommandWhat it does
preview serveServes the viewer over .3d/ on its own loopback port (default 4173). Routes: / viewer, /api/state, POST /feedback, POST /shots (merges the viewer’s camera into shots.json). The viewer reads .3d/look.json so the preview matches the chosen look, and loads three.js from a pinned CDN, so it needs network.
preview new-version --noteCreates .3d/versions/vNNN/ with a manifest.json. One version per change-set; a shown version is never edited.
preview captureFor every shot: setShot → step frames → capture → .3d/evidence/vNNN/<shot>.png. Low-resolution drafts (--size 854x480) first, 1600x900 for approval. No WebGL, a blank or constant frame, or a bridge that never becomes ready exits 1: a failed capture, not evidence.
preview diff A BTwo images or two version ids → side_by_side, blend, difference in .3d/diffs/, plus JSON with ssim and psnr_db.
preview boardBuilds a storyboard contact sheet of a version’s shot captures with ids and notes into .3d/boards/; shown to you with each version.
preview feedbackPrints your notes by version and shot from the append-only .3d/feedback.jsonl (kinds note, status, resolved; status approved or changes).
preview stopStops the preview server (reads .3d/preview.pid); run when the session ends.

Mode A · standalone

Assets under .3d/ in the skill’s own viewer. The default for assets and look-dev, and the one the agent starts itself.

Mode B · live in your app

The scene runs in your project at ?3d-preview, driven through a dev-only window.__3d bridge so capture is deterministic. Adding the bridge is a change in your repo: the agent asks first.

Your dev server stays yours. The agent never starts, kills or restarts it; it asks for the URL. It also asks before driving your app or browser unless 3D.md says capture: auto. Capture needs python playwright and your installed Chrome (no browser download), and mode B proves layout and progress, not Safari rendering.

Preflight and installs

Before any 3D work in a project with no 3D.md, a read-only pass settles what exists: capabilities writes .3d/capabilities.md (tools with cost, stack, Blender, MCP hints), the agent reads package.json and the scroll stack, picks defaults, and then asks one batched question about missing tools. It never installs without your yes.

The laws

Seven universal rules from SKILL.md; project rules (CLAUDE.md, a motion doc, decisions already in 3D.md) outrank every default.

  • Read only the routed filesA file outside the lane needs a reason you can state.
  • Detect before askingFacts come from the repo, 3D.md and .3d/capabilities.md; ask only your decisions, each with a recommended answer.
  • Never install without approvalProposed with cost labelled, run only after your yes; paid generative jobs need approval per job.
  • The dev server is yoursNever started, killed or restarted by the agent; the preview server serves .3d/ only and preview stop ends it.
  • Evidence before claimsEvery “done”, “matches” or “fast” cites a capture, a glb-report or a measurement of that claim.
  • One canonical homeDecisions, budgets, colour policy and scroll owner live in 3D.md, never a second copy.
  • Adjacent skills are recommended, never invokedscroll-animation, fluid-design, generate-image, generate-video, manufacturing-workflow, frontend.
Complementary, not duplicated: 2D scroll and DOM motion belong to scroll-animation, image and video generation to generate-image and generate-video, CAD-to-print to manufacturing-workflow. 3d owns the 3D piece, not the page around it.

Start here

Install once. Invoke as /3d (or $3d in Codex) with a request, a reference file or URL, or a GLB or .blend path; phrases like “3D hero”, “make it look like this”, “scroll-driven 3D”, “optimize this GLB”, “export from Blender” or “black R3F scene” route it too. Scripts are run as <skill>/scripts/<x> from your project root and write into its .3d/.

# skills.sh ecosystem npx skills add gabros20/3d-skill # clone + installer (per-host targets) git clone https://github.com/gabros20/3d-skill && cd 3d-skill ./install.sh codex # or: claude | agents | cursor | antigravity | opencode | grok | hermes | all # use /3d make it look like this (attach the reference) /3d optimize this GLB for a mobile hero /3d my R3F scene renders black
